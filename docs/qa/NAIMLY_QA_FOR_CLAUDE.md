# הוראות לקלוד — תיקון מערכת NAIMLY לפי דוח QA

מסמך זה מחליף את קובץ האקסל עבור Claude Code. כל הממצאים, תסריטי הבדיקה, הדרישות, ה-Benchmark והפרומפטים נמצאים בהמשך כטקסט מלא.

## סביבת העבודה

- מערכת: NAIMLY
- אתר בדיקות: https://naimly-mu.vercel.app/
- Benchmark עיצובי: https://cdbee.co.il/examples
- תאריך הדוח המקורי: 12/09/2026
- עדכון Benchmark: 13/09/2026

## תפקידך

פעל כ-Lead Full-Stack Developer, ארכיטקט מערכת, מומחה QA ומעצב Product/UI/UX בכיר. המטרה היא לא רק לשנות קוד, אלא לאתר סיבת שורש, לתקן, להוסיף בדיקות ולהוכיח שכל תוצאה צפויה מתקבלת.

cardDBee משמש נקודת ייחוס לאיכות ולמסע המשתמש בלבד. אין להעתיק קוד, DOM, CSS, טקסטים, תמונות, לוגו, מיתוג או פריסה פיקסל-מול-פיקסל. יש ליצור שפה חזותית מקורית ל-NAIMLY.

## סדר קריאת המסמך

1. קרא את סעיף תסריטי E2E והבן את מסעות המשתמש והכשלים.
2. קרא את כל הבאגים QA-001 עד QA-035.
3. קרא את הדרישות REQ-001 עד REQ-026.
4. קרא את BENCH-001 עד BENCH-010.
5. השתמש בפרומפט הייעודי של כל מזהה לפני התיקון שלו.
6. השתמש בפרומפט UX-BENCH-001 רק לאחר ייצוב השמירה, הפרסום והנתונים.

## סדר ביצוע מחייב

### קבוצה א — תקלות חוסמות ושמירת נתונים

QA-032, QA-031, QA-014, QA-015, QA-016, QA-018.

טפל קודם בשמירת טיוטה, פרסום, מניעת אובדן מידע, 404, נתוני הדמה ומד המוכנות. הצלחה תוצג רק לאחר commit אמיתי. כשל לעולם לא יאפס נתונים.

### קבוצה ב — לידים ופרטי התקשרות

QA-013, QA-024, QA-025, QA-026, QA-027, QA-033.

אחד את מקור נתוני הקשר. תקן WhatsApp E.164, רשתות חברתיות, VCard, שמירת ליד והתראות לבעל הכרטיס.

### קבוצה ג — טפסים ונגישות

QA-003 עד QA-009, QA-023, REQ-001 עד REQ-004.

הוסף labels, הודעות בעברית, aria-invalid, aria-describedby, role=alert וניהול focus. טופס אינו מתאפס לאחר כשל. סיסמה דורשת לפחות 8 תווים.

### קבוצה ד — מדיה, רקעים, QR, Slug וקבצים

QA-028 עד QA-030, REQ-008, REQ-009, REQ-019, REQ-023.

תקן העלאות, רקעים, מיקום לוגו, alt, מסמכים להורדה, QR, בדיקת Slug וחסימת מילים אסורות בצד השרת.

### קבוצה ה — שפות, חבילות, תנאים, תשלום ומדידה

QA-019 עד QA-022, QA-034, QA-035, ושאר דרישות REQ הרלוונטיות.

יישם עברית RTL ואנגלית LTR, הדרכה ראשונית, חבילות, ניסיון חד-פעמי, כרטיס נוסף, תיעוד הסכמה, תשלום ידני, Cookies, GA4, GTM ו-Meta Pixel.

### קבוצה ו — נראות הכרטיס

בצע את UX-BENCH-001 ואת BENCH-001 עד BENCH-010. התוצאה חייבת להיות Mobile First ומקורית ל-NAIMLY.

## שיטת עבודה

1. התחל ב-Audit בלבד. אל תשנה קוד לפני הצגת הארכיטקטורה, סיבות השורש, הקבצים הצפויים להשתנות והמיגרציות האפשריות.
2. צור branch בשם fix/qa-report-naimly או שם מקביל.
3. עבוד בקבוצה אחת בכל פעם. אל תנסה לתקן את כל המערכת ב-commit אחד.
4. לפני כל קבוצה ציין את מזהי QA/REQ/BENCH המטופלים.
5. אל תמחק נתוני משתמשים ואל תכניס secrets ל-Git.
6. שינוי DB מחייב migration הפיכה, בדיקת RLS, backward compatibility ותוכנית rollback.
7. אל תשנה משתני Production ואל תבצע Deploy ללא אישור מפורש.

## בדיקות חובה

לכל תיקון הוסף Unit, Integration, E2E ו-Regression לפי הסיכון. הרץ את צעדי השחזור המקוריים מתוך המסמך.

בדוק לפחות: הרשמה, OTP, התחברות, ניסיון, יצירת כרטיס, Auto Save, Reload, פרסום, Slug ציבורי, ליד, מייל, טלפון, WhatsApp, רשתות, ניווט, VCard, QR, קבצים, רקע, לוגו, שפה, Cookies, GA4, GTM, Meta Pixel, הרשאות חבילה, כרטיס נוסף ותשלום.

בדיקות תצוגה: 360px, 390px, 430px, 768px ו-1440px. אין לאשר כאשר יש overflow, חפיפות, טקסט חתוך, כפתורים שמסתירים תוכן, אזורי לחיצה קטנים מ-44px, פרטי דמה, קישורי # או אובדן נתונים.

## מתי ממצא נחשב מתוקן

ממצא ייחשב מתוקן רק כאשר סיבת השורש אותרה, התיקון יושם, צעדי השחזור עברו, נוספה בדיקה אוטומטית, Regression עבר ונשמרה ראיה. אחרת השאר אותו בטיפול, נכשל, חסום או דורש אימות.

## תיעוד

צור ועדכן את docs/qa/NAIMLY_QA_FIX_REPORT.md. לכל פריט רשום: מזהה, חומרה, סיבת שורש, קבצים ששונו, migration, תיקון, בדיקות, תוצאות, ראיה, סטטוס וסיכונים.

בסיום כל קבוצת עבודה עצור ודווח מה תוקן, מה נכשל, מה חסום, אילו בדיקות עברו ואילו פעולות דורשות אישור.

התחל עכשיו ב-Audit ובקבוצה א בלבד. אל תעבור לקבוצה הבאה ואל תבצע Deploy לפני הצגת התוצאות וקבלת אישור.

6. אם נדרש שינוי DB, צור migration הפיך ותעד backward compatibility.

בסיום החזר: סיבת שורש, קבצים ששונו, פירוט התיקון, בדיקות שנוספו, תוצאות הבדיקות וסיכונים שנותרו.

## UX-BENCH-001 — Benchmark עיצובי מול cardDBee

- מודול: נראות הכרטיס
- חומרה: גבוהה

אתה Lead Product Designer ומפתח Front-End בכיר. עבוד על מערכת NAIMLY ושדרג את הכרטיס הציבורי לרמת גימור, היררכיה וחוויית שימוש תחרותית ביחס לדוגמאות הציבוריות של cardDBee ב-https://cdbee.co.il/examples.

חשוב: cardDBee הוא Benchmark לאיכות התוצאה ולמסע המשתמש בלבד. אין להעתיק קוד, DOM, CSS, טקסטים, תמונות, לוגו, מיתוג או פריסה פיקסל-מול-פיקסל. צור שפה חזותית מקורית ומזוהה ל-NAIMLY.

יעד המוצר:
1. Hero מרשים וגמיש הכולל רקע/קאבר, לוגו או תמונת פרופיל, שם כ-H1, תפקיד/תחום, מיקום ותיאור קצר.
2. שורת פעולות קשר ברורה ונגישה: טלפון, WhatsApp, מייל, אתר, ניווט ורשתות. פעולה ללא ערך תקין לא תוצג.
3. CTA ראשי בולט לבחירת בעל הכרטיס: WhatsApp, שיחה, השארת ליד או קביעת פגישה.
4. מקטעים מודולריים: אודות, שירותים ומחירים, גלריה, וידאו, המלצות, קבצים, שעות פעילות וטופס ליד. ניתן לשנות סדר ולהציג/להסתיר בלי לאבד תוכן.
5. שמירת איש קשר מ-vCard מסונכרן ושיתוף באמצעות Web Share עם fallback להעתקת קישור.
6. ספריית תבניות מקורית לפי תחום, עם וריאציות Hero, טיפוגרפיה, רקעים ומבנה — החלפת תבנית לא תמחק תוכן.
7. Mobile First מלא: רוחבים 360, 390 ו-430px; בדסקטופ 768 ו-1440px; ללא גלילה אופקית, חפיפות או טקסט חתוך; אזורי לחיצה לפחות 44px.
8. תמיכה מלאה בעברית RTL ובאנגלית LTR, כולל טקסטים, אייקונים, סדר רכיבים ומעבר שפה.
9. WCAG 2.2 AA: HTML סמנטי, H1 יחיד, ניווט מקלדת, focus נראה, aria-label, alt דינמי וניגודיות תקינה.
10. ביצועים: תמונות responsive, lazy loading מתחת לקפל, שמירת יחס למניעת CLS ויעד Lighthouse Mobile של 90+ ביצועים ו-95+ נגישות.
11. לחבר את העיצוב לנתוני ה-Builder האמיתיים ולתצוגה החיה; אין להשתמש בפרטי NOA Studio או בערכי placeholder בחשבון חדש.
12. לשמור טיוטה אוטומטית ולוודא שכל בחירת רקע, לוגו, מיקום, תבנית ורכיב משתקפת מיד בתצוגה ונשמרת לאחר reload ופרסום.

תהליך ביצוע נדרש:
- התחל ב-Audit קצר של רכיבי הכרטיס וה-design tokens הקיימים.
- הצג לפני מימוש הצעת מבנה ורשימת קומפוננטות; השתמש בעקרונות Benchmark בלבד.
- יישם רכיבים ניתנים לשימוש חוזר עם states של loading, empty, error ו-success.
- הוסף Storybook או מסך תצוגה לכל וריאציה, אם התשתית מאפשרת.
- הוסף בדיקות Unit/Integration ו-E2E כולל השוואות צילום ברוחבים 360/390/430/768/1440.
- בדוק טלפון, WhatsApp E.164, URL חברתי, VCard, Web Share, טופס ליד, רקעים, לוגו ושינוי שפה.

תנאי קבלה:
- הכרטיס נראה מקצועי, עשיר ומוכן להצגה ללקוח כבר מעל הקפל.
- כל פעולה נבנית מהמידע הנכון ועובדת בפועל.
- אין תוכן דמה, קישורי #, חיתוך או אובדן נתונים.
- העיצוב מקורי ל-NAIMLY ואינו העתקה של cardDBee.
